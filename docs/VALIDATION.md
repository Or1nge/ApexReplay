## v0.5.0-preview 计数与伤害修复验证

这次修复针对一次实战中的两个问题：一局只杀了 1 人，片段却记为“2 名敌人”；另一局打出了爆发伤害，却没有保存。原对局没有留下录像，下面的结论来自代码复现和公开实战视频。**尚未在真实对局中复核。**

可移植部分（规则、HUD 读数、开发者记录）先在 macOS（Apple clang，C++20）上编译并运行了测试。之后在 GitHub 托管的 Windows runner 上（MSVC、.NET 10）完整构建了工作进程和界面，并跑完全部测试：

- 38 个规则场景、20 个 HUD 与开发者记录场景、8 个人声平衡场景、10 个原生场景，全部通过。新增的原生场景模拟整段保存：写入期间新数据持续进来，缓存不会被清空，已写完的数据会立即释放。
- 设置恢复测试（包括开发者模式）、命名管道测试，以及深浅两种主题的界面截图也都通过。

runner 上没有 Apex、NVENC 编码器和音频设备，所以真实采集、整段导出 MP4 和中文 OCR 还需要在实际电脑上验证。

### 1 人被记为 2 人

旧代码在下面三种情况下，会把同一个敌人先被击倒、后被淘汰算成两个人。人数凑够“多人”条件后，片段按长镜头保存：

| 情形 | 旧结果 | 新结果 |
|---|---|---|
| 击倒时读到名字，淘汰提示的名字读不出 | 长镜头，2 人 | 不保存（1 人，伤害未达标） |
| 击倒时名字读不出，淘汰时伤害恰好达标 | 长镜头，2 人 | 高伤害片段，1 人 |
| 两次名字的 OCR 结果差两个字以上（如 `Karish312` / `Kansh3l2`） | 长镜头，2 人 | 不保存 |
| 两次名字一致（对照） | 不保存 | 不保存 |

所以那一局是人数数错了，并不是击杀第一个人时就已满足保存标准。现在的规则是：淘汰先按名字找之前击倒、还没被淘汰的同一个人，较长的名字允许约四分之一的字读错；任一方名字读不出时，与 90 秒内最近一次未结束的击倒配对。名字不同的两次直接淘汰仍算 2 人。这四种情形都已作为规则场景加入 `tests/rules_tests.cpp`。

### 爆发伤害没有保存

旧检测器只要有一帧读不出右上角的伤害数字，就清空伤害基线，之后要连续 3 次读到同一个数值才重新开始计算。实战中，伤害数字一变化就会滚动，还会和亮色背景粘在一起，所以恰好在伤害增加的瞬间最容易读不出。连续开火时，数字很少能连续 3 次保持不变，结果整段战斗的伤害都没有计入，“5 秒 ≥250、其中 2 秒 >150”也就判断不出来。

现在的做法：
- 读不出数字时保留上次确认的值，读数增加需要两次一致才确认；读数大幅下降并稳定 3 次才视为新对局；不合理的跳变只更新基线，不计为伤害。
- 伤害裁剪读不出时，用整行读取（击杀、助攻、伤害）得到的伤害代替。
- 两次确认读数相隔超过 2 秒时，把这段增量按每 0.5 秒平均分摊，不当成瞬间高伤。
- HUD 读不出持续 10 秒（原为 2 秒）才算对局结束，所以打药、开地图、扔雷时不会把一场战斗拆开。观战、死亡回放、冠军等画面要持续 3 秒才算结束；状态出现“重置”时立即结束。武器名“和平捍卫者”不再被误认成冠军提示。

### 当前版本 HUD 调研

参考视频：YouTube “High Level Seer Gameplay - Apex Legends (No Commentary)”（Silent Gaming，Season 30，4K，英文 HUD）。在浏览器中把 4K 画面缩到 1920×1080 后分析。下面的坐标都是 1080p 坐标，和 GPU 分析画面一致：

- 右上角计数行（y≈99–118）从左到右依次是：骷髅图标和击杀数、握手图标和助攻数、爆炸图标和伤害。整行右对齐，伤害数字右缘固定在 x≈1754。本局第一次击杀或助攻之前，击杀和助攻那一块不显示，只有伤害。原有伤害裁剪仍然对准伤害数字，现有字形模板也能识别当前字体。
- 在同一段战斗里，原有伤害读取（3 个二值化阈值）约 14% 的帧读不出，换成 5 个阈值约 8%。读不出的帧集中在数值变化的时候。新版本保留原有的伤害裁剪读取，读不出时再用 5 个阈值的整行读取。
- 击杀信息（右上，y≈216–296）每行依次是：战队标签、攻击者、武器图标、受害者。击倒行在武器和受害者之间多一个红色向下箭头，淘汰行没有。
- 中央结果提示的主行位于 y≈769–786，在原有 OCR 裁剪范围内。

新的整行读取在两帧真实画面上都读对了，分别是击杀 5、助攻 1、伤害 1194，以及击杀 15、助攻 4、伤害 3919。旧的伤害读取在这两帧上都读不出。这两帧只在本地评估，不随源码或运行包分发。仓库里的测试用字形模板合成画面。

## v0.4.0-preview 人声平衡验证

人声平衡在开发容器（Linux x86-64，g++ 13 -O2）中用同一份 C++ 代码离线验证；Windows 构建和全部测试由发布工作流在 Windows 上编译运行。**尚未在真实 Apex 对局、真实 Discord/KOOK 语音和真实麦克风上做主观听感验收。**

- 公开真实录音（只用于本地评估，不随源码或运行包分发）：3 段 LibriSpeech 朗读（女声中位基频约 196 Hz，男声约 82 Hz 和 140 Hz），各按 3 个电平输入。人声帧检出 89–95%；输出人声响度 −20.8 至 −23.5 LUFS，只有需要超过 +24 dB 增益的 −50 LUFS 输入停在 −26.1 LUFS。另有英语、法语、汉语、TIMIT 短句，正常电平输入后输出 −19.4 至 −21.6 LUFS；一段乐器音乐只有 15% 帧被视为人声，增益不超过 +1 dB。
- 提示音：10 个真实系统提示音（KDE Ocean 声音主题，含多音和弦、混响和扫频起音）单独播放时，人声帧 0–7.7%，都没有被当作说话音量学习。67 秒混合测试中把 16 个响亮提示音插在小声说话之间：提示音增益 0 dB（一个为 −2.1 dB），测得的说话音量与没有提示音时相同（−46.0 LUFS），人声输出 −20.8 LUFS（无提示音时 −20.6）。
- 换人说话：小声说话后 10 秒静音，再换成响 26 dB 的说话人，第一秒 −14.7 LUFS、3 秒后 −19.7 LUFS；随后再换成小声说话人，5 秒后 −22.4 LUFS。
- 合成场景 8 个（`tests/speech_tests.cpp`）：三种音量收敛、高低音高检出、五类合成提示音、噪声与键盘声不放大、带背景噪声的说话、换人与长时间静音、平衡偏移与 Apex 音轨仅限幅、时间戳断点。原生测试另覆盖限幅、时间戳连续和持续底噪不被抬高。
- 开销：每条音轨约 0.55% 的单核 CPU（上述环境），音频延迟约 0.3 秒但时间戳不变；导出会等待三条音轨追上片段结尾（最多 1.5 秒）。

## v0.3.0-preview 验证

- 两段近期实战素材分别处理 204、215 个观察帧，均得到两次本人击倒和一个人数为 2 的长镜头计划。第一段修复前离线可重现 3 人；第二段的原实时日志为 3 人，错误来自同一提示的名字恢复/截断。根因包括 OCR 掩码滤掉红色名字、0.9 秒漏读即重建临时身份，以及把名字片段当作新敌人。现在红色名字保留、字幕区域排除、临时身份补充名字时合并，并要求快速的新名字有新的战斗证据。
- 早期两段素材分别确认一次击倒，以及一次助攻加一次击倒。后者原日志曾在同一助攻之后因 OCR 漏掉“助攻”前缀而额外记一次击倒；不能把原文件的“2 人”标签当成两次独立本人击倒。新增回归覆盖前缀丢失、前缀恢复后纠正已有事件，及采集启动时可见的旧提示。
- 高伤害规则：5 秒累计 ≥250，且同一窗口中 2 秒伤害 >150。边界 250 可通过、150 不通过；仅满足一项不通过；超过 5 秒的旧伤害不计入；跨换弹/切枪、技能伤害及高伤害助攻通过。纯伤害无结果提示不导出，符合条件的单次击倒可导出，普通连杀合并和 90 秒分段继续通过。
- 应用设置在立即退出及两次新进程中恢复，包括四项伤害标准与开机自启偏好。隔离启动测试确认无需点击录制按钮便进入“等待 Apex”；WPF 集成测试确认等待、开始、停止、音频状态、托盘隐藏及退出。
- 深浅两种外观均渲染检查概览、保存标准及通用设置；音量平衡轨道和红色滑块可见，片段标题使用主题文字颜色。真实短采集测试编码 361 帧并完成 HEVC MP4 导出，60 fps、三个 AAC 音轨、隐藏采集边框及三个音频设备健康状态通过。此短测试不是游戏性能基准。

原始录像保持不变。诊断位于本地源码工作区 `artifacts/bug-v0.3.0`，不随公开运行包分发。上述样本仍不能证明总体精度或覆盖所有模式、名字和分辨率。
